# 자유 건축 — 새 설계 초안

> ⚠️ 2026-10-05 제작자 지시로 §8 시제품(`building_test.map`)은 폐기. 현행 설계는 [building-system-v2.md](./building-system-v2.md) — 이 문서의 확정 사항·점유 규칙(§3)은 v2가 이어받는다.

2026-10-05. 이전 건축 설계와 아트는 폐기했다. 이 문서는 새 출발점이며, **자유 건축**은 제작자 확정, 아래 구현 구조와 수치는 제안이다. 게임 기능은 아직 구현하지 않는다.

## 1. 만들고 싶은 경험

영지에서 나무를 모아 바닥을 깔고 벽과 문으로 방을 만든다. 그 안에 이미 있는 침대·상자·조리 냄비·화로를 배치한다. 집의 모양과 크기는 플레이어가 정하고, 철거해 다시 꾸밀 수 있다.

첫 목표는 **작은 집 하나를 짓고 생활 가구를 놓을 수 있는 상태**다. 첫 버전은 영지 한정, 목재 한 세트, 한 층. 지붕·실내맵 이동·벽 내구도·침입 몬스터·다층 건축·집 등급·대량 드래그 설치는 후속 후보로 둔다. 기존 RPG 진행 보상이나 날씨 시스템에 새로운 효과를 확정하지 않는다.

## 2. 기본 구조 — 반복되는 벽은 타일

제작자의 오브젝트 수 증가 우려를 설계 조건으로 반영한다.

| 요소 | 우선 표현 | 역할 |
|---|---|---|
| 바닥 | 비충돌 타일 | 지면을 덮으며 벽·가구와 같은 셀에 공존 |
| 일반 벽 | 충돌 타일 + 필요한 타일 외관 | 통행 차단·인접 벽 연결. 벽 한 칸마다 엔티티를 생성하지 않음 |
| 문 | 상태를 가진 오브젝트 | F로 열기/닫기, 문 셀의 통행과 벽 연결에 참여 |
| 작업대·가구 | 기존 모델 기반 오브젝트 | 제작·수납·회복 등 개별 상호작용 |

일반 벽에는 칸별 스크립트·Trigger·OnUpdate·개별 RPC를 붙이지 않는 방향이다. 서버는 셀 데이터와 타일 변경을 관리한다. 타일 렌더링의 드로콜 수·메모리 절감 배수·허용 최대 수량은 측정 전이므로 확정하지 않는다. 엔티티가 줄어도 타일·점유·저장 데이터의 비용은 남는다.

공식 패키지와 로컬 위키 카탈로그를 검토했다. 건축에 직접 대응하는 패키지는 카탈로그에서 찾지 못했다. 인벤토리·제작·저장·권한은 프로젝트의 기존 구현을 재사용한다.

## 3. 바닥 위에 가구를 놓는 규칙

현재 `GridToEntity`는 한 셀에 한 점유 슬롯이다. `ResourceSpawner.AddPlacedTile`은 이 슬롯에 바닥을 기록하고, `PlayerInventory.ServerRequestPlace`는 슬롯이 존재하면 가구 배치를 거부한다. 바닥 타일을 추가하는 것만으로는 집 안 가구 배치가 되지 않는다.

새 건축 데이터에서 **바닥 기록과 구조물 점유를 분리**한다. 기존 일반 자원·가구 점유 레지스트리는 연동하되, 바닥으로 그 슬롯을 덮어쓰지 않는다.

| 아래 지면 | 위 설치물 | 허용 |
|---|---|---|
| 건축 바닥 | 없음 | 이동·벽·문·가구 배치 가능 |
| 건축 바닥 | 벽 또는 닫힌 문 | 이동·다른 구조물 배치 불가 |
| 건축 바닥 | 가구 | 기존 가구의 점유·통행 규칙 적용 |
| 건축 바닥 | 자원/작물 | 새 자원 리스폰·파종 불가 |

- 첫 버전에서 바닥은 비어 있는 건조 지면에만 설치한다. 물·맵 밖·자원·작물·플레이어가 점유한 셀에 설치하지 않는다.
- 벽과 문은 바닥이 있는 셀에 놓는다. 기존 벽과 가구, 플레이어와 겹칠 수 없다.
- 문이 열려도 문 설치 셀의 구조물 점유는 유지한다. 통행 허용과 배치 허용은 구분한다.
- 철거 대상은 바닥/구조물을 명시해서 선택한다. 위에 벽·문·가구가 있으면 바닥 철거를 거부한다.
- 설치·철거 뒤 자원 리스폰 판정은 바닥과 기존 점유 정보를 함께 확인한다. 가구 철거가 아래 바닥의 보호까지 해제하지 않게 한다.

## 4. 플레이 흐름과 재료

제안 흐름: **목공 작업대 제작 → 작업대에서 바닥·벽·문 제작 → 기존 배치 모드로 설치 → F로 문 출입 → 생활 가구 배치**.

작업대는 영지 성장의 작은 목표로 제안한다. 구 설계의 작업대 수치나 해금 조건은 이어받지 않는다. MVP에서는 작업대 접근이 항상 가능한지 먼저 확인한다.

- 초기 콘텐츠: 목공 작업대 1종, 목재 바닥 1종, 목재 벽 1종, 나무 문 1종. 외관 변형이 아이템 종류를 늘리지는 않는다.
- 비용 제안: 작업대 Wood 8 + Stone 2, 바닥 Wood 1 → 4개, 벽 Wood 1 → 1개, 문 Wood 3 → 1개. 수치와 산출량은 구현 시 데이터셋으로 관리하며, 이 문서의 제안만으로 게임 데이터를 바꾸지 않는다.
- 건축 철거는 설치 자재를 반환하는 방향. 설치 실패 시 소비하지 않거나 즉시 환불한다. 인벤토리가 가득 찼을 때의 반환은 기존 보상/드롭 규약을 확인한 후 확정한다.
- 이동은 방향키, 배치 모드에서 Ctrl은 바라보는 인접 셀 설치, 문·작업대 상호작용은 F. 일반 상태의 Ctrl 공격·채집을 유지한다. 별도 건축 단축키는 추가하지 않고 기존 배치 진입 경로를 확인한다.
- 영지 소유자/손님 권한 검사는 서버에서 수행하고, 배치 프리뷰와 거부 사유는 클라이언트에서 표시한다.

## 5. 벽 높이와 캐릭터 가림 — 먼저 검증할 항목

입체감은 바닥과 구분되는 윗면, 앞면의 높이, 모서리·기둥 연결, 접지 명암에서 만든다. **점유 칸은 1×1**, 개별 타일 이미지 규격은 **64×64px**. 필요하면 여러 64px 타일로 시각적인 높이를 표현하되, 높이·칸 이동량·레이어 수는 작은 방에서 확인한 뒤 정한다.

`RectTileMapComponent`의 `SortingLayer`와 `OrderInLayer`는 타일맵 단위 속성이다. 개별 벽 타일마다 아바타와 앞뒤 정렬을 할 수 있다고 가정하지 않는다. 이는 타일 위주 설계에서 가장 먼저 해결해야 할 시각적 제약이다.

우선 작은 방에서 낮은 벽부터 시험한다. 북쪽 벽 앞·남쪽 벽 뒤·코너·문틀에 선 플레이어가 읽히는지 확인한다. 높이를 늘려 가림이 나빠지면, **충돌은 유지하면서 앞을 가리는 벽의 표시를 낮추는 타일 표현**을 검토한다. 개인별 표시 변경은 별도 클라이언트 표시 레이어와 동기화 간섭 여부를 Maker에서 확인해야 하며, 아직 가능하다고 확정하지 않는다.

한 셀 벽에 앞면·윗면 스프라이트 엔티티를 각각 만드는 방식은 기본안으로 삼지 않는다. 타일만으로 필요한 가림 표현을 달성하지 못하면 그 결과와 제한을 보고하고, 표현 높이를 줄이는 안과 제한적인 오브젝트 보조안을 비교한다.

## 6. 연결·표시·저장 데이터

- 저장의 기준은 **설치한 논리 요소**다: 바닥/벽/문, `item_dataset.Name` 아이템 키, 셀 좌표, 필요한 문 상태, 스키마 버전. 타일 이름이나 RUID로 게임 규칙을 판별하지 않는다.
- 외관은 데이터셋에서 요소 유형·재질·이웃 연결 상태에 대응시킨다. 코드에 특정 아이템 이름 분기나 임의 RUID를 하드코딩하지 않는다.
- 설치·철거 시 변경 셀과 주변 연결 상태만 갱신한다. 4방향 연결에 대각선 모서리까지 필요하면 3×3 범위를 갱신 대상으로 한다. 영지 전체 스캔을 매 프레임 하지 않는다.
- 문 셀은 열림/닫힘과 무관하게 벽 연결의 문틀 자리로 취급한다. 닫을 때 플레이어와 겹치면 닫기를 거부한다.
- 전체 자료구조 리팩터링을 전제하지 않는다. 새로운 바닥 기록과 기존 점유/자원 리스폰의 접점만 추가하는 방향으로 검토한다.
- 복원은 논리 배치 로드 → 점유 복원 → 연결 계산 → 타일/문 표시 → 이동 가능 상태 확인 순서다. 재입장 시 중복 엔티티·중복 등록이 없어야 한다.
- 기존 저장 경로와 같은 중요 이벤트 플러시를 활용한다. 필수 GetAndWait/SetAndWait 외 추가 Yield를 넣지 않는다.
- 기존 `Wood Floor` 키·기존 설치 기록은 삭제하지 않는다. 새 바닥과의 변환/호환은 구현 시 별도 검사하고, 기존 세이브를 초기화하지 않는다. 현재 `Baram_167` 타일 이름과 설치 레이어의 타일셋 불일치 가능성은 배치 조사에서 재확인할 항목이다.

## 7. 아트 제작 순서

이전 목업·타일·v번호는 재사용하지 않는다. 먼저 임시 타일로 작은 방의 기능과 화면 문법을 검증한다. 다음에 **방 전체 콘셉트 1장**으로 기존 잔디·아바타·가구와 그림체를 맞추고, 마지막에 실제 연결 타일을 만든다.

목재는 메이플 카툰 명암과 자연스러운 재질을 기준으로 한다. 바닥은 중간 밝기의 편안한 목재, 벽은 더 짙은 목재, 밝은 테두리는 광원 쪽에만 둔다. 재질 질감을 노이즈로 채우거나 모든 모서리에 같은 굵기의 선을 긋지 않는다. 게임 배율에서 읽히는 나뭇결·부품 명암을 우선한다. 반복 바닥의 변형 수와 연결 타일 수는 시제품 결과로 정한다.

공식 리소스·기존 리소스를 먼저 검토하고 필요한 부분만 새로 제작한다. 제작자가 새 그림체를 검토하기 전 타일 세트를 양산하지 않는다.

## 8. 검증과 구현 순서

1. **시각·충돌 시제품**: 바닥 5×5 내부 공간과 한 칸 두께의 외벽, 문 하나. 북벽·남벽·세로벽·코너·문 출입과 캐릭터 가림을 제작자가 Play에서 확인한다. 타일 렌더 구조를 여기서 확정한다.
2. **점유 시제품**: 바닥 위 상자·침대 설치, 벽/문과 가구 중복 거부, 가구 철거 후 바닥 유지, 바닥 철거 거부 조건, 자원 리스폰 보류를 확인한다.
3. **성능 확인**: 벽 100/500/1000칸의 시험 배치에서 문 수는 동일하게 두고 입장·복원 시간, 이동 중 프레임, 한 칸 설치/철거 지연, 저장 데이터 크기를 측정한다. 수량은 시험 조건이며 지원 한도가 아니다. 벽 수에 비례하는 엔티티나 매 프레임 콜백이 생기지 않는지 확인한다.
4. **정식 제작**: 아트·데이터 확정 → 작업대·제작 → 설치·철거 → 문 → 저장·복원 → 권한·프리뷰·거부 피드백.
5. **회귀 확인**: 기존 영지 포탈, 가구, 작물, 자원 리스폰, 손님 권한, 세이브. 정적 검사 → refresh 상태 → 이번 갱신 시각의 빌드 로그 확인. Play는 제작자 수행.

현재 상태: 설계 승인 후 **1단계 격리 시제품 코드·시험 맵 작성**. `map/building_test.map`에서 기존 등록 바닥·벽 타일과 문 오브젝트를 사용한다. 지면/설치물 점유 분리·정식 설치/철거·아트·저장은 아직 미구현이다. [시험 진입과 확인표](./building-prototype-checklist.md). LSP 오류 0, 빌더 구조 검사 통과, Maker refresh ok, 신규 `.codeblock` 생성 확인. **build 로그 갱신 미확인**, **런타임 검증 보류(제작자 수행)**.
